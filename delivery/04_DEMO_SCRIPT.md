# 04 — Final demonstration script

A concise demonstration should show one continuous customer problem, not a catalogue of features.

## Before the meeting

- Check out the release branch/commit and run the documented offline reproduction.
- Keep the actual model inference status explicit. Offline demo data is not a live answer.
- Choose one public case with a confirmed product and documentation edition.
- Keep the original question, official passages and reviewer-only reference separate.
- Have one source-linked video ready for Phase 2.
- Do not display private support data, API keys or unreviewed model claims.

## Walkthrough

### 1. Show the two channels

Explain that the same system is intended for:
- a customer who calls support and later becomes an out-of-scope ticket;
- a developer who posts a question on the forum and may wait for an answer.

Both should be handled by the same evidence and answer pipeline. The support-ticket route accepts only approved sanitized samples; no live ticket system is connected.

### 2. Phase 1: ask whether existing knowledge is enough

Open a real original question. Show the product/version context, the official TechDocs passages and sample code. Show what is allowed into the model and what is held out for review. Generate or replay an actual saved answer only if the run receipt exists.

### 3. Show the disposition

Demonstrate one of:
- direct documented guidance;
- a focused clarification;
- a documented limitation/out-of-scope answer;
- human escalation because evidence conflicts or a device check is required.

Explain that model candidates are not confirmed resolutions until reviewed.

### 4. Show the cross-case contribution

Show how a repeated failure pattern becomes a bounded answer strategy: what to check, which context to request, which source to cite and when to abstain. Explain that evolutionary strategy selection is experimental and has not yet been evaluated on real reviewed runs.

### 5. Phase 2: show the video

Use the EHS 4.0 settings-access lesson or another reviewed source-backed concept. Explain the distinction being taught and open the exact source. State that the current five encoded clips prove the rendering pipeline works; they do not prove improved learning.

### 6. End with the enterprise result

The intended loop is:
1. answer eligible current questions automatically;
2. route uncertain cases safely;
3. compare cases to identify recurring confusion;
4. improve the relevant documentation or answer strategy;
5. create a visual explanation when a concept is hard to understand;
6. test the improvement on new cases.

Close with the remaining evidence gates: live approved model runs, independent review, document-revision comparison, held-out strategy evaluation and customer acceptance.
